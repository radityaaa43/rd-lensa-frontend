# Lensa in the cluster: manifests (plan S4-S6)

Source of truth: `final-design/lensa/PLAN.md` in platform-exploration. These files render the objects of S4a (`base`), S4b (`volume`) and S6 (`app`) for namespace `rd-lensa` on cluster 1. Nothing here talks to a cluster.

```bash
deploy/k8s/test.sh                        # offline test: bash + python3 + PyYAML
deploy/k8s/render.sh base                 # namespace, default-deny, DNS and gateway egress policies, SAs and Roles (entry A)
deploy/k8s/render.sh volume               # PVC lensa-state 5Gi, StorageClass rd-retain-essd (LENSA_STORAGE_CLASS overrides)
LENSA_IMAGE=ghcr.io/radityaaa43/rd-lensa-frontend@sha256:<digest> LENSA_ENV_FILE=<file> deploy/k8s/render.sh app
```

- Entry A is the default (user answer L1): ClusterIP only; viewers use `kubectl -n rd-lensa port-forward svc/lensa 8790:8790` with a token of SA `lensa-access`. `LENSA_ENTRY=b` renders the CLB ingress policy instead (not planned).
- `gateways.conf` is the egress allow-list. It is empty until each platform's gateway step names its pod label and ports; empty renders a policy with no egress rule (deny). Bank C is one `/32` per public gateway load balancer; its address is not committed, the operator passes it in an extra file through `LENSA_GATEWAYS` at apply time. The sinks share the gateway listener, so there is no separate sink rule.
- Secrets are never rendered. Their owners create them, create-only: `ghcr-pull` (a copy of the existing cluster-1 Secret), `lensa-gw-mtls-bi|a|b|c` (keys `ca.crt`, `lensa.crt`, `lensa.key`). The pod mounts them at `/certs/<BI|A|B|C>/` and does not start when one is missing. Also `lensa-sink-token-bi|a|b|c` (key `token`, 64 hex characters, no newline; each party creates only its own), mounted read-only at `/sink-tokens/<BI|A|B|C>` with mode 0440 behind `LENSA_SINK_TOKENS_DIR`. The ConfigMap sets `OPA_BIN=/usr/local/bin/opa` (the one pinned opa of the image: a rego tester / tar tool, no signing key; a live policy publish from the pod stays refused) and `LENSA_IN_CLUSTER=1`: the server then refuses `KUBECONFIG`, `OPA_KEYS_DIR` and similar, and accepts the token files in this read-only mount (PR #69).
- The ConfigMap `lensa-env` takes gateway URLs and Besu doors from `LENSA_ENV_FILE` (allow-listed keys only; a value with `@`, a quote, a backslash or a space is refused: no credentials in URLs).
- The image must be a ghcr digest reference of `ghcr.io/radityaaa43/rd-lensa-frontend`; a tag is refused.

Not verified offline [unverified until S4a/S6 run]: that the cluster CNI lets `kubectl port-forward` reach a pod under `default-deny-all` (kubelet-originated traffic is normally exempt); the CoreDNS label `k8s-app=kube-dns`; the pod's real CPU and memory (the numbers in `templates/app.yaml` are starting values).

Cluster 1 today: `rd-retain-essd` does not exist there, so `lensa-state` runs on `alicloud-essd-wffc` (applied with `LENSA_STORAGE_CLASS=alicloud-essd-wffc`). That class deletes the disk with the claim, so after the first bind (the S6 pod) only that PV's `spec.persistentVolumeReclaimPolicy` is patched to `Retain`.

Probes: startup and liveness use `/api/livez`, readiness uses `/api/readyz` (503 until a model loaded, so an unseeded state keeps the pod Running and out of the Service instead of restarting it).
- `render.sh dryrun` (not part of `all`): ConfigMap `lensa-candidate` (the 8 verified Kebijakan bundle sources + the expect file, public data only: the render refuses key-like member names, PEM key content, a stray file or a sha256 mismatch) and Job `lensa-dryrun` (label `app=lensa-dryrun`, never `app=lensa`; TTL; no egress, no certs, no tokens read). It runs `policy-publish --candidate` WITHOUT `--apply` in pod mode on the read-only mount: "candidate verify in pod mode, no sink IO". Needs `LENSA_IMAGE`, `LENSA_CANDIDATE_DIR`, `LENSA_CANDIDATE_EXPECT`.
- `render.sh seed` / `seedcheck` (not part of `all`): the state seed of the PVC `lensa-state`. `seed` takes `LENSA_SEED_DIR` = a staging dir written by `seed-state --out` (server/src/cli/seed-state.ts) and renders ConfigMap `lensa-seed` + Job `lensa-seed` (no egress, label `app=lensa-seed`, affinity to the node of the lensa server pod because the PVC is ReadWriteOnce): it copies EACH file by its explicit name (never a directory) and runs `sha256sum -c`. The render refuses any path outside the allow-list (zeto, noto, the policy store: no stealth, no iroha3), key-named fields, PEM, a stray or missing file and a manifest that disagrees; it prints file names + sha256 (never content) to stderr. `seedcheck` renders a no-egress READ Job that greps the PVC (read-only) and the image data files for PRIVATE KEY / privateKey / spendKey / viewKey / seed and prints names + sha256 only; expected `grep hits: 0`.
- `render.sh probe` (not part of `all`): the egress proof Job `lensa-egress-probe`, from `LENSA_PROBE_TARGETS` (lines `host port`: Service names or single IPv4 hosts such as the bank C load balancers). The pod carries `app=lensa` (the real `egress-party-gateways` policy applies) and `role=egress-probe` (Service `lensa` needs `role=server`, so it never selects the probe; cleanup selector). Fixed in the template: negatives 1.1.1.1:443 and the API server ClusterIP:443, a positive `dns.lookup` via kube-dns, a negative resolver to 8.8.8.8:53. No volume but /tmp, no Secret, no token; deadline 120 s, TTL 120 s.
